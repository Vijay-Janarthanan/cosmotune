# Local library tools for 1.0.4 (in development)

Listening tools → Backup & transfer now exports the current queue's local files or the local library to UTF-8 M3U8. Android uses its document chooser with the playlist MIME type; desktop uses the native save dialog. Queue order and repeated tracks survive. A queue track can resolve a saved local file through its exact source-qualified recording ID in the library; no title-based substitute is chosen.

Only readable absolute file paths or file URIs are exported. Online-only recordings, missing files, signed HTTP addresses and device-only content-provider links are skipped and counted. Metadata cannot inject extra playlist lines. Exports are limited to 10,000 tracks and 4 MiB, include local file locations and do not copy audio or carry credentials. Moving a playlist to another device requires copying the music and adjusting its locations. This is a local playlist export, separate from listening metadata backup and from linked-playlist synchronization.

Two format/filesystem tests pass Unicode filenames/metadata, duration parsing, order/duplicates, directive injection protection, skipped counts and limits. An actual Compose interaction passes queue-to-download lookup and platform chooser handoff; Android production and desktop Kotlin compile. The real OS chooser and another player's import still need a walkthrough. Tag editing, duplicate/repair review, quality upgrades and linked synchronization remain separate tracker work.

Desktop save operations now retain the expected metadata-file extension and publish through an adjacent temporary file, fsync and atomic replacement where supported. A referenced audio file or local manifest cannot be selected as its own M3U8 export destination. Two additional filesystem/failure-injection checks pass preserving an existing backup on interrupted output, cleaning partial files, retaining the correct suffix and preventing source audio/manifest replacement. Desktop compilation passes. The interrupted local run was replaced by a successful bounded, in-process build.

## Library review in progress

Listening tools now has a Library review tab on both native hosts. Its bounded read-only scan checks local filesystem locations and Android content-provider grants, distinguishes missing, empty and permission-restricted files, and detects container signatures independently of filename extensions. Filters cover measured format, problem state and title/artist/album/source text. This is header evidence, not decoded bitrate, a spectral audit or proof of the original master.

Duplicate groups distinguish aliases of one canonical file, SHA-256-identical files and matching metadata candidates. Byte comparisons stream 64 KiB chunks, skip files outside the explicit default 2 GiB comparison budget, check size/modification/identity after reading, and honor cancellation. Different editions and encodings are never automatically merged. No audio is removed or replaced by this review. Reports explicitly contain local locations and are capped at 16 MiB; remote stream addresses and error details are excluded.

Saved-session repair previews use readable local copies with the exact source-qualified recording ID. Apply checks the original entries and replacement availability again before one atomic store update; duplicate queue entries, position, shuffle/repeat and other metadata survive. This repairs session references, not the download registry or filesystem. Updates now read the latest durable state under a shared path lock, use unique adjacent temporary files and preserve the original on failure. A preview cannot overwrite a correction saved by another open window.

The final focused run passed **29 tests, zero failures/errors/skips**: five audit/repair checks, eleven store checks, two network checks, four M3U8/atomic-output checks and seven actual Compose interactions. The new UI scan/export/preview/apply test renders a screenshot at `uiTests/build/reports/listening-ui/library-review.png`. Android release/debug/test-source and desktop compilation passed at the preceding checkpoint; the subsequent minified Android rebuild includes the latest store/availability safeguards. Its actual startup/mode-switch checks are still pending. Tag editing, actual duplicate merging/removal, moved-file fingerprint reconciliation, decoder-based quality audits, lossless replacement, genre columns and linked playlists remain outstanding.

## Library loudness, quality, tags, merges and linked playlists (1.0.4, cx-a3)

**Loudness (MN-06).** Listening tools → Library review → *Analyse local audio* decodes each readable local file once and measures ITU-R BS.1770-4 / EBU R128 integrated loudness (K-weighting, 400 ms blocks with 75 % overlap, -70 LUFS absolute and -10 LU relative gates), sample peak, ReplayGain 2.0 track gain (-18 LUFS reference), decoded codec/rate/bit depth/bitrate and the highest frequency still carrying energy. The meter is Cosmotune's own code written from the recommendation. Desktop decodes through the same FFmpeg decoder as playback; Android uses MediaCodec; RIFF/WAVE PCM is read in shared Kotlin on both. Results are stored beside the listening data (`cosmotune-library-analysis.json`, local locations and figures only, atomic replacement) and reused while a file's size and modification time are unchanged. Playback on both hosts uses the measured figure for local files when loudness normalization is on, in the same units as YouTube's stated loudness (dB above -14 LUFS), limited so a boost cannot push the measured peak above -0.1 dBFS; the existing per-track limiter remains. Files are never modified. Each scan also records ReplayGain 2.0 album gain and album peak for tracks sharing an album and album artist (from the file's tags, else the library entry): the album's loudness is the duration-weighted energy mean of its tracks' gated loudness, which usually agrees with a pooled-block measurement within a few tenths of a LU because the per-track blocks are not kept. Library review shows it beside the track gain; playback keeps per-track normalization, which matches the existing stream behaviour.

**Quality evidence (LK-08, LK-09).** The same analysis labels each file *Lossless decode*, *Lossy decode* or *Possible lossy source* (a lossless decode at 44.1 kHz or more whose spectrum stops below 19 kHz). This is evidence for review, never proof of an original master. The review list now filters by measured quality and by the container's genre tag, beside the earlier format/problem/text filters.

**Tags, duplicate merges (MN-08, LK-12).** *Edit tags* rewrites FLAC Vorbis comments or MP3 ID3v2.3/2.4 text frames (title, artist, album, album artist, genre, track, year) with Cosmotune's own writer. Audio bytes and every other block/frame are copied unchanged; the result is written beside the file, re-read and verified, then atomically replaces it, and a file that changed meanwhile is left alone. Ogg Vorbis and Opus comments are rewritten too: only the comment packet changes, the header pages after the identification page are re-paginated, later pages of the stream are renumbered with fresh CRCs, and their payloads, segment tables and granules are verified unchanged. MP4/M4A `ilst` items are rewritten (text items, `trkn` as number/total, `gnre` replaced by a text genre); a `free` box after `moov` absorbs growth where it can, otherwise every `stco`/`co64` chunk offset is moved, and the media bytes are verified by digest. Fragmented MP4, multiplexed Ogg, unsynchronised/extended ID3 headers and damaged layouts are refused and the file is left untouched. Android rescans the file afterwards; content-provider files that Cosmotune cannot write report that instead. For groups whose bytes were verified identical, *Keep this copy* previews and applies saved-session location changes (recording IDs, queue entries and history unchanged) and can then move the other copies to the system trash: desktop through the operating system's trash, Android 11+ through MediaStore's own trash confirmation for shared-storage media. Similar-metadata candidates are never merged.

**Linked playlists (LK-11).** Listening tools → *Linked playlists* links a public YouTube Music playlist. *Check for changes* computes a three-way merge (last synced source, this device, current source) and shows it before anything is saved: local removals, additions and order win; source additions are inserted after their nearest source predecessor; removed or unplayable source rows become greyed placeholders (ghosts) that keep identity, likes and history and are restored if the source brings them back; repeated recordings are matched by occurrence. A response with far fewer rows than last time is flagged as possibly partial. A stale preview cannot overwrite a later edit. Playing a linked playlist is library-first: same-ID or unambiguous local copies play from the device and the rest stream (the result is reported).

**Metadata fallback (LK-10).** Desktop local files now read FLAC/MP3 tags; a missing artist falls back to the album artist, an "Artist - Title" file name, then an Artist/Album folder layout for numbered tracks (generic folders are never used). Android applies the same rule to MediaStore rows (album artist on Android 11+). Listeners can add their own one-artist names (for example "Shankar, Ehsaan & Loy") in Library review; matching and listening statistics keep them whole on both hosts.

Remaining library limits: decoder analysis on Android is compiled but not run here (no emulator in this session); Android tag edits only apply to files Cosmotune can write; MP4/Ogg tag editing, album gain, provider-based lossless replacement and moved-file fingerprint reconciliation are not implemented.

## Sources, columns, scrobbling, lyrics and players (1.0.4, cx-a4)

**Subsonic and OpenSubsonic (MN-07).** Settings → Sources → *Add a Subsonic server* (both hosts, one shared dialog) takes the server address, user name and password, or an API key on OpenSubsonic servers, and checks the server before saving. The credential is kept with the source list (Android encrypted preferences; Windows DPAPI-sealed preferences on desktop; on macOS and Linux desktops the same preferences as add-on settings, not the platform keychain) and is never shown again. The server is a user-added source: it can be reordered with the add-ons, it is offered rows from YouTube to substitute with the listener's own copy, it answers the Addons search on Android, and *Browse* opens its songs, albums and artists in the shared catalogue browser; album links on its rows open through the same pages. Streams are the stored files (`format=raw`), lossless included; the stream address carries a fresh token and is handed to the decoder only, never logged or stored, and cover art is not fetched because Subsonic cover addresses carry the credential. Desktop SMB and WebDAV stay a recorded decision: shares mounted by the operating system are scanned as local folders.

**Library columns and filters (LK-09).** The main local library song lists (Android Local Music and Downloads; desktop Local Music and Downloaded) have a shared bar: *Columns* adds album, length, source, format, quality, loudness and genre to each row, and filters narrow the list by source (this device, network share, own server, streaming), measured quality and genre. Format, quality, loudness and genre come from the local analysis; unanalysed rows fall back to the file name. Each list keeps its own choice.

**Download registry repair (LK-12).** At start-up each host checks its saved-download records. A record whose file is gone is pointed at the one audio file with the same name in the library and download folders that no other record claims (two candidates are never guessed between); the rest stop counting as downloaded and appear in the download manager as failed with *Retry*. Nothing is fetched until the listener asks, and no file is moved or deleted. Android repairs `file://` records this way; `content://` records keep their existing recovery when a read fails.

**Recap share card and mini player (LK-14, LK-19).** Desktop Replay has *Share card*: a 1080 x 1920 card with the period, minutes, plays and the top five songs and artists, saved as PNG through the system file picker. The desktop mini player is a small always-on-top window (artwork, title, artist, progress, previous, play/pause, next, back to the main window), opened from the tray menu or with Ctrl/Command+Shift+M.

**ListenBrainz retry (LK-20).** Finished ListenBrainz listens on both hosts now go through the shared offline queue used by Last.fm: network failures, server errors, rate limiting and a rejected token keep the listen (metadata only) and send it before the next one, in order; a listen the service refuses as invalid is dropped. Queued ListenBrainz listens are kept up to six months, Last.fm's two weeks. Token review: Android keeps the Last.fm session key and ListenBrainz token in app-private preferences, desktop in the user's Java preferences; neither is in the platform secret store yet, and neither ever enters the queue file.

**Save lyrics as .lrc (MN-09).** The lyrics share flow on both hosts has *Save as .lrc*, which writes the whole song's lyrics (not only the picked lines) with `[ti:]`, `[ar:]`, `[al:]` and `[length:]` headers, a stamp per line, enhanced `<mm:ss.xx>` word stamps where the provider timed words, and background vocals as their own lines in parentheses. Untimed lyrics are written as plain lines.


## Provider-based lossless copies and delivered-format checks (cx-p1)

Library review on both hosts can now ask the enabled sources for lossless copies of analysed lossy entries (*Get lossless copies from sources*). Only catalogue or source-qualified recordings without a verified lossless copy are queued, at the LOSSLESS rung. Every finished download is labelled from its own bytes by the shared `DeliveredAudio` check: a FLAC claim over AAC keeps no lossless badge, an unverified claim is dropped, and a web page saved as audio fails the download. After the next analysis, *Preview lossless upgrades* offers only copies measured as lossless without a lossy-source spectrum; audio files are never overwritten. Real providers were not used to check this.
