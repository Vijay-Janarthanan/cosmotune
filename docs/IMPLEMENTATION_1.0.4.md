# 1.0.4 implementation scope

The user explicitly requested on 2026-10-23: implement every feature in [FEATURE_TRACKER.md](../FEATURE_TRACKER.md) in one coordinated effort, then push and release 1.0.4. Do not publish the current native/watch subset as the completed release. No v1.0.4 commit/tag/release has been pushed yet.

## Work sequence

1. Finish native integration and verify Android/Desktop/Wear packaging. Preserve the existing model, OpenCanvas and platform fixes.
2. Manga: shared module, local CBZ/image reading, persisted progress, Kotatsu source integration, catalogue/chapter/reader UI, downloads/storage, custom and Android extension sources, optional Komga.
3. Provider contracts/runtime: catalogue capabilities and cache refresh, Mornye package/repository support over existing platform script engines, constrained host APIs/session configuration, source-specific download pacing/recovery.
4. Discovery: provider-fed regional shelves, Last.fm/YouTube account candidates, tiny local online preference learning and repeat/diversity controls; preserve the under-5-MB model target and benchmark phones where available.
5. Library: metadata/artist identity, quality/source/genre filters and columns, duplicate review, tag editing/export, linked playlist sync/ghosts, missing-download repair, quality audit and reviewable upgrades, recap/share expansion.
6. Integrations/output: authenticated network music sources, loudness scanning, device-specific exclusive/DSD paths, Cast receiver/desktop support, Soulseek/slskd, authenticated LAN remote, concerts/haptics/widgets/backups and configurable account integrations.
7. Complete upstream native UI/functional gaps, app icons/onboarding, TV profiles/PIN and web/helper extension features, while retaining Cosmotune branding and design. A module move or redraw is not a feature by itself.
8. Validate all tracker rows against source, tests and runtime evidence. Measure final packages, verify signing/models/imports, update README/notices/ledger/tracker, then commit, push and publish 1.0.4 once the release gates are met.

These stages are implementation order, not separate partial releases. Features needing an external account/server or physical hardware must provide complete configuration/error handling and record what was actually tested; fixture tests and compilation must not be described as live provider/device verification.
