# Music download recovery for 1.0.4

Implemented in the working tree; not published yet. Android and desktop retain requested music downloads in a versioned, atomically written local journal. It stores track metadata, ask order, requested quality and failure state. Expiring audio addresses and stream credentials are resolved again rather than saved in that journal.

Reopening the app shows interrupted jobs for **Retry**. It does not automatically start network transfers. Retry preserves the requested quality. Completed/cancelled intents leave the journal; failures remain visible. A damaged journal is left untouched and the download manager displays a storage error. The journal is capped at 2,000 entries and 4 MiB. It is separate from the library's record of completed files.

Queue admission reserves at most two workers per source-qualified provider, with four workers overall, so a third job for one provider cannot occupy another provider's free worker. Resolved transfers also have a provider-specific two-transfer limit and a 500 ms start gap. Ordinary catalogue IDs share a pre-resolution lane; after resolution the configured source or download host selects the transfer lane. Playback requests are not delayed by this download-only policy.

Each attempt has a sequence number. Progress, failures, completion and slot release from a cancelled attempt cannot overwrite a retry with the same track ID. Desktop transfers run in child jobs, so cancelling a song leaves its queue worker available. Storage errors are visible in both download managers.

Recovery here means retaining the user's requested work. Android's destination transaction still aborts incomplete output and retries that file from the beginning. Desktop ordinary audio and provider workspace downloads now share validated transfer logic: a strong ETag or Last-Modified checkpoint, hashed address identity, exact contiguous Content-Range/length and byte budgets precede append; completion is atomic. Changed/invalid ranges discard partial bytes, an ignored Range restarts cleanly, and changed signed addresses force a clean transfer. Checkpoints do not contain raw stream addresses. Manifest downloads rebuild their output. Files already successfully published retain the existing saved-file lookup. New desktop filenames include a short recording/source/quality identity to prevent title-only collisions or reusing a lower requested rendition. Existing files are not renamed.

## Checks

The combined follow-up passed: 8 shared journal/pacing/learning tests, 10 desktop queue tests, 35 Android download tests and 3 Android emulator runtime tests. Queue tests use isolated fake transfers, never the user's Music folder or live providers. They cover a cancelled worker, cross-provider fairness and late progress after retry. Journal tests cover restart/order/quality/failures, obsolete completion and corrupt-file preservation. Pacing tests use a virtual clock and cover concurrency, start spacing and cancellation.

Cross-process Android service termination and real source transfers still need a complete app walkthrough. Five additional desktop tests use real isolated HTTP fixtures for exact-range resumption, changed validators/ranges, cross-origin credential stripping, cancellation of a blocked read followed by a successful retry, and rendition identities. These tests never touch the user's Music directory. Provider transfer regression tests also pass after sharing the validation core. Manifest transfer follow-up is described below; complete service/device walkthroughs remain.

## Segmented audio follow-up

Phone and desktop HLS/DASH downloads now share checked raw HTTP transport: 2 MiB manifests, 32 MiB segments, 65,535 media segments and 4 GiB total input. Redirects strip source headers on a different origin, HTTPS cannot downgrade, and cancellation closes the blocked request and joins its worker. The shared parsers reject excessive/overflowed timelines, unsupported encrypted/live/partial layouts and external HLS side references. Unsupported layouts fail explicitly.

Desktop M4A assembly builds the seek table from bounded fragment headers and copies audio in 32 KiB chunks instead of loading the whole assembled recording. Phone offline packages publish a fresh generation after all segments and the local playlist are written; a failed retry cannot erase a completed package, and Java hash collisions cannot select another song. Existing saved paths keep working. Unreferenced generations after a process crash and full service/restart cleanup still need the repair/storage-management walkthrough; no automatic deletion of a user's completed generation was added.

Five desktop fixture tests pass indexing against the previous byte-array reference, cross-origin segment/redirect headers, oversized chunked manifests, blocked-read cancellation, malformed/encrypted input and temporary cleanup. Three Android JVM checks pass generation preservation, hash/quality separation and malformed/live/encrypted input alongside the existing DASH/FLAC/M4A tests. These are controlled filesystem/HTTP checks, not a claim of real-service transfer completion or physical-device testing.

## Failure paths follow-up (cx-p1)

A desktop transfer that was cancelled by something other than the listener (a timeout inside the transfer) used to be treated like a listener's cancel and left its row Running in the manager and the saved queue; it is now a visible failure with Retry. Three new `DesktopDownloadQueueTest` cases cover a failed transfer being saved with its reason, Retry asking for the originally requested quality after the default changed, the timeout case, and a restored journal that offers interrupted and failed work without fetching anything until Retry. The tests inject the default quality and use a temporary journal file, never the user's settings or Music folder.
