# Local phone/browser remote (1.0.4 implementation in progress)

The shared `remote` module is being integrated for desktop and TV. Its server binds one selected, locally assigned private or loopback IPv4 interface and uses an ephemeral random 256-bit pairing key. The pairing link carries the key in a URL fragment; the page removes that fragment and sends authenticated API requests with a bearer header. It does not accept an account cookie, reveal audio URLs or auto-start on launch.

The self-contained page has playback/previous/next, position, volume and music search/play controls. The browser receives temporary opaque track IDs, not internal recording IDs or local paths; the server resolves them to the native host's entries. Desktop integration exposes Listening tools → Phone remote, with interface selection, a pairing QR/private link and Stop. Its window owns the controller; closing the settings alone leaves an enabled remote running. Player commands dispatch to the main thread through existing user-intent/party handlers, and library replacements respect Listen Together state. TV Settings → Connections adds the same paired protocol with native queue/library and YouTube Music search; opening the account picker or changing profiles closes its session, and locked profiles require their own verification.

Wire handling caps headers at 8 KiB, request bodies at 8 KiB, API responses at 512 KiB, search results at 50 and remembered track IDs at 500. Four workers, a 16-request queue, read/deadline limits, exact Host/Origin checks, no CORS allowance, POST-only typed commands and per-start key rotation bound exposure. Stop cancels callbacks and closes active/queued clients. This is an explicitly enabled local HTTP control channel; keep pairing links private and use it on a trusted LAN. It does not stream the audio to the browser.

The pinned [BitChord TV server](https://github.com/kushagrasinghx/BitChord/blob/edc1e6f36febf71a118e649411d2fc21b70ead45/tv/src/main/java/com/music/bitchord/ui/tv/auth/TvAuthServer.kt) has unauthenticated status/actions/search/play/cookie submission, wildcard CORS and unbounded per-client threads. Cosmotune's integration must use the shared paired remote rather than import that server as-is. The 55-file upstream TV module and its two PIN test files are hashed in the ignored audit record `build/upstream/tv-port-audit.json` at revision `edc1e6f36febf71a118e649411d2fc21b70ead45`.

Call-path review found that normal upstream TV setup/account callers disable phone sign-in, and the legacy server is started only from that branch; its native playback/status callbacks are not assigned in the module. This review does not claim a normally exposed remote in the running upstream app. Cosmotune's new desktop integration has actual native player callbacks and explicit pairing controls.

Seven real loopback HTTP/lifecycle/controller tests passed for authentication, origin/host/method rejection, wire/command limits, session-owned track selection, stop/restart, app-window ownership and callback cancellation/error redaction. An actual Compose settings interaction also passed starting a real server, using its QR link's key for status/control, stopping clients and rotating the next link. Desktop and Android compilation passed in the 2m21s integration run. A real browser with an isolated two-track host fixture passed play/pause, seek, volume, search/result playback, disconnected controls and keyboard focus restoration. The fixture is not proof of physical playback or a QR camera scan. TV D-pad navigation reached its native remote dialog and started a loopback session; independent QR decoding exposed an inherited encoder defect, now being replaced with the existing phone/desktop codec. Final native remote/browser and physical-network checks remain. CI/release commands include the module; no release has been published.
