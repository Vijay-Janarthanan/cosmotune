Pinned source: [BitChord TV at `edc1e6f36febf71a118e649411d2fc21b70ead45`](https://github.com/kushagrasinghx/BitChord/tree/edc1e6f36febf71a118e649411d2fc21b70ead45/tv). The adapted `tv` module is included in the Android build; `tv/UPSTREAM_IMPORT.json` records the 43 imported files and excluded/replaced assets. It is not released yet.

## Feature inventory

The module reuses phone playback/account/data code and replaces its entry UI with a remote-first TV activity. Its separate code covers TV setup/personalization, Home/search/library/album/artist/browse screens, a full player and queue/lyrics views, D-pad focus/navigation and dialogs, account/profile selection, per-profile PINs, PIN failure throttling, USB music integration, refresh-rate/display capabilities, spatial/sound-check preferences, typography/layout scaling, update prompts and a QR phone connection/remote. Watch bridge/installer implementations deliberately provide no TV/watch pairing. Phone compilation alone cannot validate these TV features.

`TvSettings` stores salted PBKDF2-HMAC-SHA256 PIN hashes (120,000 iterations), constant-time verification and legacy hash/plaintext migration; two upstream test files cover PIN persistence and throttling. The port must retain those tests, initialize TV settings before playback, and verify profile gates across warm/cold startup, account changes and failed attempts.

## Integration findings to address

* The upstream LAN server implements unauthenticated status, playback, search, play and cookie-submission routes, wildcard CORS, and a new thread for every client. The normal setup/account callers pass `allowPhoneSignIn = false`; the only source-level start call is inside the disabled phone-sign-in branch, and no native playback/status callbacks are assigned in this module. This is legacy code, not proof of a working exposed remote in the normal upstream TV flow. Cosmotune's shared paired remote is being implemented separately. Account transfer must not be implemented as plaintext cookie submission through that server; native TV sign-in is a separate existing flow.
* The source manifest places the `.MainActivity` alias before its `.TvActivity` target. Android requires the target declaration first. Reorder it in the port and verify the final merged manifest/install rather than assuming source ordering is repaired by the merger. See the [official activity-alias contract](https://developer.android.com/guide/topics/manifest/activity-alias-element).
* TV has its own package/update asset prefix. Its update picker must select TV assets, never install a phone APK. Use Cosmotune's release version/signing configuration and preserve the phone/watch identities.
* The TV build reuses phone source/resources/native libraries, substitutes duplicate Kotlin paths, and declares Compose TV dependencies. Port against Cosmotune's actual current dependencies, source paths, backup rules and module graph. Do not use the upstream hardcoded public Listen Together deployment as a Cosmotune default.
* Reuse Cosmotune branding/resources and record all adaptations. Original authorship/licence headers remain. Do not silently introduce extra font/image assets without checking their redistribution terms.

## Implementation checkpoint

Release and debug Kotlin compilation pass. Twenty-three TV tests pass: eight throttle checks, eleven PIN/preferences checks, two profile verification-state checks, one QR decoder check with long/UTF-8 inputs and one effect resource-lifecycle check. Removing one account now removes only that account's profile PINs, and verified access belongs to a particular profile rather than a process-wide boolean. Opening account controls revokes that verification. Invalid PIN shapes, malformed stored hashes and excessive PBKDF work factors fail closed.

The original paired LAN module supplies the TV remote. Its native adapter dispatches player operations on the main thread, enforces party controls, checks the live account/profile scope before every request and bounds search results/cached recordings. Leaving the allowed profile closes the session. Settings expose network selection, start/stop and a QR pairing link. TV sign-in remains a separate native flow.

The target activity now precedes its alias. TV updates select only TV APKs in supported ABI order, with universal fallback; phone updates exclude TV/watch assets. TV reuses the root release version/key and current native dependency graph, excludes the embedded Wear APK, and uses existing/system fonts and a vector banner. The shared mood renderer is reused without a phone layout change. TV's 24 fps preference selects eligible video renditions; it is not a guarantee that a decoder drops frames when only a higher-rate rendition exists.

All four signed packages pass identity/version/certificate/entry/ABI checks against the production phone key, plus recommendation/OpenCanvas verification. A minified x86_64 checkpoint cold-launched in 1,606 ms on the dedicated Android 36 phone AVD in landscape. D-pad onboarding/public Home/settings and the remote dialog pass. The original custom QR failed independent decoding; it is replaced by the phone/desktop codec, and the actual rendered QR now decodes. The initial remote text inherited the wrong Material foreground; explicit TV colours fix it. Spatial Audio's setting now observes/attaches/releases the real audio session instead of merely toggling unused state, and defaults off. USB routing text no longer promises unchanged/exclusive output.

A real paired browser searched public YouTube Music, started Manasavacha by Unni Krishnan/Chitra from Godavari, observed advancing playback, sought to 40 seconds, changed volume to 25% and paused at 78,841 ms. Opening account controls closed the connection; the browser showed the disconnect and disabled every action. Evidence lives in ignored `build/upstream/tv-native-remote-proof.json`, `tv-fixed-*.xml/png` and `tv-browser-remote-disconnected.png`. This is a phone AVD, not a TV system image, physical remote or speaker listening test. AndroidRuntime's final capture includes a `UiAutomation` bad-file-descriptor shell error during WebView capture; it is not an empty log and does not identify a Cosmotune app crash. A process-filtered follow-up is still appropriate.
