## Notes

- Invite links: `cosmotune://party/<CODE>` works as soon as the app is installed. The web address `https://cosmotune.github.io/invite/<CODE>` will not open the app until that site serves invite pages and publishes an app-link (`assetlinks.json`) file for our signing certificate.
- The backend now builds `cosmotune://party/...` deep links and its page text says Cosmotune, but none of that Go was compiled or tested (no Go toolchain on the build machine): a human has to run `go build` and `go test` in `backend/` before relying on it. Still upstream in the backend: the Go module path (`github.com/KabirSinghBhatia/BitChord/backend/...`, kept so the imports and `go.mod` stay valid), the log line `BitChord Listen Together (Go) starting` and the `service` name in `main.go`, and `backend/deploy/` (clones upstream's repository, example host names).
- Names and ids (Task 5): what people read, what the app files itself under and what it announces to the system is Cosmotune's own (`ForkGuardTest` checks it). Kept on purpose, because they are internal and renaming them would make every upstream merge conflict: the packages `com.music.bitchord` and `namespace`, class names such as `BitChordApplication` and `BitChordIcons`, the `bitchord.*` system and Gradle properties, the `BITCHORD_*` environment variables, the `bitchord://` internal stream scheme, `bitchord_window` / `bitchord_analysis` / `bitchord_smtc` native libraries, `bitchord-app.jar`, `Theme.BitChord`, resource keys such as `widget_open_bitchord`, log tags (`"BitChord"`), the `com.music.bitchord` MP4 tag namespace in `Mp4Tagger.kt`, and the backup tag in `Backup.kt`.
- Linux: `StartupWMClass=com-music-bitchord-desktop-MainKt` in `appimage.sh` is derived from the main class, which we keep (jpackage derives the same value for the `.deb` and `.rpm` desktop entries). A Linux dock may therefore group Cosmotune and BitChord windows into one icon; it cannot be fixed without renaming the main class.
- Windows media controls: the hidden window that the native media-control (SMTC) library creates is still called `BitChordSmtcWindow` / `BitChord` in `desktopApp/native/smtc/smtc_abi.cpp` and `smtc_jni.cpp`. It is not shown to people, and the library is compiled from source (a C++ toolchain is needed to check a change), so it was left; rename it together with the library when the native build is next run.
- CI paths and names after the rename: changing `packageName` to `Cosmotune` moved the jpackage app-image folder from `desktopApp/build/compose/binaries/main/app/BitChord/...` (and `BitChord.app`) to `.../app/Cosmotune/...` (and `Cosmotune.app`), and the installers were still copied to `BitChord-$v-...` names, so every workflow that names the folder or the files had to change. `check.yml` was fixed in Task 7 (see its row above). Task 9 fixed `.github/workflows/release.yml` (see its row): the six places that named the folder (the jar checks of the three desktop jobs, the AppImage input of `appimage.sh`, the Windows portable zip input and the macOS `ditto` zip input), the nine output names (`Cosmotune-$v-linux-x86_64.AppImage`, `-linux-amd64.deb`, `-linux-x86_64.rpm`, `-windows-x64.msi`, `-windows-x64-setup.exe`, `-windows-x64-portable.zip`, and `-macos-<arch>` with `.dmg`, `.pkg` and `.zip`) and the release title (`Cosmotune <tag>`); it also gained the `android` job (four signed APKs) and the macOS step "The app starts" (a start-up check of 25 seconds, `continue-on-error`). These are edits of our fork only: upstream's `release.yml` still says `BitChord`, so every upstream merge that touches the file has to be checked against its row.
