## Notes

- Invite links: `cosmotune://party/<CODE>` works as soon as the app is installed. The web address `https://cosmotune.github.io/invite/<CODE>` will not open the app until that site serves invite pages and publishes an app-link (`assetlinks.json`) file for our signing certificate.
- The backend now builds `cosmotune://party/...` deep links and its page text says Cosmotune, but none of that Go was compiled or tested (no Go toolchain on the build machine): a human has to run `go build` and `go test` in `backend/` before relying on it. Still upstream in the backend: the Go module path (`github.com/KabirSinghBhatia/BitChord/backend/...`, kept so the imports and `go.mod` stay valid), the log line `BitChord Listen Together (Go) starting` and the `service` name in `main.go`, and `backend/deploy/` (clones upstream's repository, example host names).
- Names and ids (Task 5): what people read, what the app files itself under and what it announces to the system is Cosmotune's own (`ForkGuardTest` checks it). Kept on purpose, because they are internal and renaming them would make every upstream merge conflict: the packages `com.music.bitchord` and `namespace`, class names such as `BitChordApplication` and `BitChordIcons`, the `bitchord.*` system and Gradle properties, the `BITCHORD_*` environment variables, the `bitchord://` internal stream scheme, `bitchord_window` / `bitchord_analysis` / `bitchord_smtc` native libraries, `bitchord-app.jar`, `Theme.BitChord`, resource keys such as `widget_open_bitchord`, log tags (`"BitChord"`), the `com.music.bitchord` MP4 tag namespace in `Mp4Tagger.kt`, and the backup tag in `Backup.kt`.
- Linux: `StartupWMClass=com-music-bitchord-desktop-MainKt` in `appimage.sh` is derived from the main class, which we keep (jpackage derives the same value for the `.deb` and `.rpm` desktop entries). A Linux dock may therefore group Cosmotune and BitChord windows into one icon; it cannot be fixed without renaming the main class.
- Windows media controls: the hidden window that the native media-control (SMTC) library creates is still called `BitChordSmtcWindow` / `BitChord` in `desktopApp/native/smtc/smtc_abi.cpp` and `smtc_jni.cpp`. It is not shown to people, and the library is compiled from source (a C++ toolchain is needed to check a change), so it was left; rename it together with the library when the native build is next run.
- CI paths and names after the rename: changing `packageName` to `Cosmotune` moved the jpackage app-image folder from `desktopApp/build/compose/binaries/main/app/BitChord/...` (and `BitChord.app`) to `.../app/Cosmotune/...` (and `Cosmotune.app`), and the installers were still copied to `BitChord-$v-...` names, so every workflow that names the folder or the files had to change. `check.yml` was fixed in Task 7 (see its row above). The workflow has been read, parsed (`yaml-lint`) and checked against `ForkGuardTest`, but not run: the first run on GitHub (Run workflow, version `1.0.0-alpha1`) is the real test, and the four secrets `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD` have to be set in the repository first.
- Data kept apart from an installed BitChord, in one place for reference: Windows registry `HKCU\Software\JavaSoft\Prefs\com.cosmotune.desktop` (and `.stats`); `~/.local/state/cosmotune/desktop.log`, `~/.cache/cosmotune/media`, `~/.local/share/cosmotune/analysis` (the same dot-folders under the user's home on Windows); `~/Music/Cosmotune`; the keyring attribute `application=cosmotune`; the MPRIS bus name `org.mpris.MediaPlayer2.cosmotune`; on Android the package `com.cosmotune.app` / `com.cosmotune.dev` and the folders `Music/Cosmotune` and `Pictures/Cosmotune`. The OpenCanvas maps (`<trackVideoId>_<videoId>.json`) live in `~/.cache/cosmotune/media/opencanvas` on the desktop and in the app's own `files/opencanvas` on Android.
- Android 12+ splash (icons task): there is no splash library and no splash drawable; the system shows the launcher icon on `windowSplashScreenBackground`. `app/src/main/res/values-v31/themes.xml` and `app/src/main/res/values-night-v31/themes.xml` are new files of ours (so they have no row above): each is `Theme.BitChord` with the same parent as upstream's (`Theme.AppCompat.DayNight.NoActionBar`), the black `android:windowBackground` that `values/themes.xml` and `values-night/themes.xml` already set (the window is black before Compose draws, in both themes, so there is no white flash), and `android:windowSplashScreenBackground` and `android:windowSplashScreenIconBackgroundColor`, both black. Both files are needed because Android picks `values-night/` before `values-v31/` for a phone in dark mode. A style of the same name in a more specific folder replaces the whole style, so an item that upstream later adds to `Theme.BitChord` in `values/themes.xml` or `values-night/themes.xml` does not reach Android 12 and up unless it is copied into these two files as well: check them after a merge that touches either theme file.
